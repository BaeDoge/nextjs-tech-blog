## 모델을 작게 만들면 실제 서비스도 빨라질까요?

LLM을 사내 서버나 개인 GPU에서 운영하려고 할 때 가장 먼저 부딪히는 문제가 GPU 메모리입니다. 모델 가중치만 해도 수십 GB를 차지할 수 있고, 입력 문맥과 생성 중인 토큰을 보관하는 KV 캐시까지 더해지면 필요한 메모리는 더 커집니다.

이 문제를 줄이는 대표적인 방법이 **양자화(Quantization)**입니다. 모델의 가중치를 더 적은 비트로 표현해 메모리 사용량을 낮추는 방식이죠. 하지만 가중치를 4비트로 줄였다고 해서 모든 작업에서 정확도가 그대로 유지되거나 응답 속도까지 빨라지는 것은 아닙니다.

이번 연구는 이 차이를 바이오 의료 자연어 처리(BioNLP) 작업에서 비교했습니다. 핵심 질문은 단순히 '얼마나 작아지는가?'가 아니라, **모델·작업·추론 엔진에 따라 메모리, 정확도, 지연 시간, 출력 형식이 어떻게 달라지는가?**입니다.

## 양자화 실험은 어떻게 구성했을까요?

연구진은 먼저 Hugging Face Transformers와 BitsAndBytes를 이용해 가중치 정밀도를 낮췄습니다. 기준이 되는 Full Precision 모델과 8비트, 4비트 모델을 같은 작업에 적용해 성능과 메모리 사용량을 비교했습니다.

```flow
원본 LLM 체크포인트
→ Full Precision 기준 성능 측정
→ BitsAndBytes로 W8A16 또는 W4A16 로드
→ 동일한 프롬프트와 데이터셋으로 추론
→ 정확도·Peak GPU Memory·Latency·출력 유효성 측정
→ 모델과 작업별 양자화 결과 비교
```

여기서 W4A16은 가중치를 4비트로 저장하고 연산은 16비트 정밀도로 수행하는 설정입니다. W8A16은 가중치가 8비트인 경우예요. 4비트 설정에는 NF4 방식과 FP16 연산, Double Quantization을 사용했습니다.

| 설정 | 가중치 표현 | 연산 정밀도 | 주요 목적 |
|---|---:|---:|---|
| Full Precision | 기준 모델 설정 | 기준 설정 | 비교 기준 |
| W8A16 | 8bit | 16bit | 메모리 절감과 성능 균형 |
| W4A16 | 4bit | 16bit | 가중치 메모리 최대한 절감 |

<Callout type="tip" title="4비트가 항상 더 좋은 선택은 아닙니다">
  가중치 메모리를 더 줄일 수는 있지만, 실제 작업 점수와 출력 품질은 모델마다 다릅니다. 특히 이 연구에서는 일부 바이오 의료 특화 모델이 8비트 설정에서 반복되거나 의미가 불분명한 출력을 만드는 현상도 관찰했습니다.
</Callout>

## 어떤 작업으로 모델을 평가했을까요?

평가에는 8개 데이터셋을 사용했고, 이를 네 가지 작업으로 나눴습니다. 같은 모델이라도 작업의 성격에 따라 양자화 영향이 다를 수 있기 때문에, 하나의 평균 점수만 보는 대신 작업별 결과를 비교했습니다.

| 작업 | 데이터셋 | 평가 지표 |
|---|---|---|
| 다중 라벨 분류(MLC) | HoC, LitCovid | Macro F1 |
| 개체명 인식(NER) | BC5CDR, NCBI Disease | Entity F1 |
| 관계 추출(RE) | ChemProt, DDI | Macro F1 |
| 질의응답(QA) | MedQA-USMLE, PubMedQA | Accuracy |

모델이 정답을 맞혔는지만 확인한 것도 아닙니다. 생성 결과가 비어 있거나 파싱할 수 없는 형식인지, 같은 문장을 반복하는지도 기록했습니다. 실제 서비스에서는 점수가 조금 높더라도 응답을 후처리할 수 없는 형태로 내놓는다면 운영하기 어렵기 때문입니다.

## 메모리는 줄었지만, 지연 시간은 별도로 봐야 합니다

논문에서 확인한 큰 흐름은 4비트와 8비트 양자화가 GPU 메모리 사용량을 줄이는 데 효과적이었다는 점입니다. 특히 4비트는 더 큰 메모리 절감 효과를 보였고, 여러 작업에서 평균 성능 변화도 비교적 작았습니다.

그렇다고 모든 모델과 작업에서 성능 차이가 작았던 것은 아닙니다. 일부 바이오 의료 특화 모델은 8비트 설정에서 지시를 제대로 따르지 못하거나 반복적인 출력을 만들었습니다. 따라서 모델별 결과를 확인하지 않고 '4비트 또는 8비트로 바꾸면 성능이 유지된다'고 일반화하면 안 됩니다.

여기서 구분해야 할 점이 하나 더 있습니다. **모델 가중치 메모리와 추론 중 전체 GPU 메모리는 같은 값이 아닙니다.** 실제 추론에서는 활성화 값, CUDA 실행 환경, KV 캐시 등이 추가 메모리를 사용합니다. 논문도 프롬프트에 예시를 추가하는 Few-shot 설정에서 KV 캐시 사용량이 늘어날 수 있다고 별도로 분석합니다.

## vLLM에서는 AWQ·GPTQ·FP8도 비교했습니다

연구진은 BitsAndBytes 실험과 별도로 vLLM을 이용한 서빙 실험도 진행했습니다. 여기서는 AWQ, GPTQ, FP8 체크포인트를 Qwen2.5-7B와 Qwen2.5-32B 모델에 적용하고, 일부 대표 데이터셋에서 정확도와 생성 토큰 처리량을 비교했습니다.

```flow
양자화 체크포인트 준비
→ vLLM 서빙 엔진으로 모델 로드
→ 동일한 작업 데이터로 배치 추론
→ Task Score와 Tokens / Second 측정
→ AWQ · GPTQ · FP8 결과 비교
```

이 실험은 앞의 BitsAndBytes 실험과 같은 기준으로 메모리를 직접 비교하기 위한 것은 아닙니다. vLLM은 서빙을 위해 GPU 메모리를 미리 확보하고 KV 캐시도 관리하기 때문에, 메모리 사용 방식이 다르기 때문입니다.

결과적으로 모든 작업에서 가장 좋은 단일 양자화 방식은 나오지 않았습니다. 모델 크기와 작업, 추론 엔진에 따라 결과가 달랐기 때문에 실제 서비스에 적용할 때는 목표 환경에서 직접 비교해야 합니다.

## 프롬프트 길이와 출력 품질도 운영 비용에 포함됩니다

모델 가중치를 줄였다고 GPU 메모리 문제가 끝나는 것은 아닙니다. Few-shot 예시를 프롬프트에 추가하면 입력 토큰이 늘어나고, 추론 과정에서 KV 캐시가 차지하는 메모리도 커집니다.

Chain-of-Thought(CoT)나 Self-Consistency처럼 여러 단계의 추론 또는 여러 출력을 활용하는 방식도 마찬가지입니다. 정확도가 개선될 수 있지만 생성 토큰과 응답 시간이 늘어날 수 있습니다.

따라서 실제 서빙 환경에서는 양자화 설정만 비교할 게 아니라 다음 항목을 함께 측정해야 합니다.

- **정확도:** 대상 업무에서 원본 모델과 비교해 성능이 얼마나 달라지는지
- **Peak GPU Memory:** 모델 가중치 외에 추론 중 필요한 메모리까지 포함하는지
- **Latency:** 요청 한 건을 처리하는 데 걸리는 시간
- **Throughput:** 초당 생성 토큰 수와 동시 요청 처리량
- **Output Validity:** JSON이나 정해진 응답 형식이 깨지거나 반복되지 않는지

## 공개 코드로 확인한 구현 구조

논문은 실험 코드를 [Learner4everrr/Benchmark_quantization](https://github.com/Learner4everrr/Benchmark_quantization)에 공개하고 있습니다. 저장소의 README는 Conda 환경과 `requirements.txt` 설치를 안내하지만, 실행 예시에 적힌 `benchmark.py` 파일은 현재 저장소 루트에서 확인되지 않습니다. 실제 루트에는 `main.py`가 있으므로 README의 실행 예시를 그대로 따라 하기 전에 코드와 문서를 대조해야 합니다.

확인한 `main.py`는 `--model`, `--dataset`, `--quantization` 인자를 받고, `--gen`과 `--eval`로 생성과 평가 단계를 실행합니다. `model_manager/quantization.py`에서는 BitsAndBytes 설정을 구성합니다.

```flow
main.py
→ model / dataset 인자 검증
→ ModelBase 생성
→ get_model_kwargs()에서 양자화 설정 구성
→ Transformers 모델 로드
→ 데이터셋 추론 및 결과 JSON 저장
→ 평가 지표·메모리·Latency·Throughput 계산
```

예를 들어 코드에 등록된 `Qwen2.5-7B` 모델과 `hoc` 데이터셋을 선택하는 명령 형태는 다음과 같습니다.

```bash
python main.py --model Qwen2.5-7B --dataset hoc --quantization 4bit --gen
python main.py --model Qwen2.5-7B --dataset hoc --quantization 4bit --eval
```

다만 이 명령을 실행하려면 저장소가 요구하는 Python 패키지와 CUDA 환경, 모델 가중치 접근 권한, 데이터셋 준비가 필요합니다. 위 명령은 실제 실행을 검증한 결과가 아니라 `main.py`의 인자 정의와 실행 흐름을 바탕으로 정리한 예시입니다. README의 `benchmark.py` 안내와 실제 파일 구성이 일치하지 않는 부분도 있으므로, 저장소를 그대로 재현 환경으로 사용하기 전에는 먼저 실행 경로를 확인하는 편이 안전합니다.

## 실험 결과를 실제 서비스에 적용한다면

이 연구에서 가져갈 만한 결론은 '무조건 4비트가 정답'이라는 추천이 아닙니다. 양자화는 가중치 메모리를 줄이는 데 유용하지만, 최종 서비스 품질은 모델과 작업, 프롬프트 길이, 추론 엔진에 따라 달라집니다.

특히 논문은 주요 실험을 NVIDIA A100 40GB GPU 네 장을 사용해 수행했다고 밝힙니다. RTX 소비자용 GPU를 직접 비교한 연구는 아니므로, 이 결과만으로 특정 개인용 GPU에서 70B 모델이 안정적으로 동작한다고 단정할 수는 없습니다. 실제로 논문도 소비자용 GPU별 처리량이나 지연 시간, 전력 사용량을 직접 측정하지 못했다는 한계를 설명합니다.

개발 환경에서 양자화를 검토한다면 먼저 서비스가 요구하는 정확도와 응답 형식을 정하고, 같은 입력 데이터로 Full Precision·8bit·4bit를 비교하는 것이 좋겠습니다. 그 다음 실제 운영할 추론 엔진에서 KV 캐시와 동시 요청까지 포함해 메모리와 처리량을 측정해야 합니다.

이 논문은 범용 양자화 기법을 새로 제안한 연구라기보다는, 바이오 NLP라는 특정 도메인에서 여러 모델과 작업의 양자화 trade-off를 비교한 벤치마크 연구입니다. 따라서 핵심 가치는 하나의 양자화 방법을 정답으로 제시하는 데 있지 않고, 배포 전에 어떤 지표를 함께 확인해야 하는지 구체적인 평가 관점을 제공한다는 데 있습니다.
