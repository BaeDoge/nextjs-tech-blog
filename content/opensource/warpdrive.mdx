## 한눈에 보는 프로젝트

WarpDrive는 웹 애플리케이션에서 서버 데이터를 다루기 위한 타입 기반 데이터 라이브러리입니다. 공식 README는 이 프로젝트의 방향을 범용성, 타입 안정성, 반응성, 확장성으로 소개하며, 프레임워크에 걸친 반응성, 다양한 API 사용, SSR 지원을 주요 목표로 제시합니다.

다만 README의 목표 문구만으로 모든 프레임워크와 데이터 소스에서 같은 기능이 동일한 수준으로 지원된다고 단정해서는 안 됩니다. 실제 도입 전에는 사용 중인 프레임워크와 WarpDrive 릴리스의 호환성 표, 설치 가이드, 해당 패키지 문서를 함께 확인해야 합니다.

## 이해에 필요한 핵심 개념

WarpDrive는 애플리케이션의 서버 데이터를 모델과 캐시를 중심으로 다룰 수 있도록 구성합니다. 여기서 중요한 것은 단순한 전역 상태 저장소와 달리, API에서 받아온 데이터의 구조와 생명주기, 캐시 접근을 데이터 계층에서 일관되게 관리하려는 점입니다.

공식 저장소에는 모델 관련 API, 어댑터, 캐시 타입 등 역할이 나뉜 패키지가 있습니다. 예를 들어 JSON:API를 사용하는 애플리케이션은 해당 어댑터 패키지를 검토할 수 있습니다. 다만 이 예제가 GraphQL이나 모든 REST API를 자동으로 지원한다는 뜻은 아닙니다. 실제 API 연동 범위는 개별 어댑터와 사용 가이드에서 확인해야 합니다.

## 저장소 코드에서 확인한 레거시 호환 방식

현재 저장소에는 과거 Ember Data 경로를 유지하면서 새 패키지 경로를 안내하는 재수출 파일이 있습니다.

~~~typescript
// packages/model/src/hooks.ts
export {
  instantiateRecord,
  teardownRecord,
  modelFor,
  buildSchema
} from '@warp-drive/legacy/model';
~~~

이 파일의 주석은 기존 @ember-data/model/hooks 사용 경로를 호환 목적으로 유지한다고 설명합니다. 새로운 코드에서는 @warp-drive/legacy/model 경로를 사용하도록 안내합니다.

JSON:API 어댑터도 같은 방식으로 재수출됩니다.

~~~typescript
// packages/adapter/src/json-api.ts
export {
  JSONAPIAdapter as default
} from '@warp-drive/legacy/adapter/json-api';
~~~

캐시 타입의 레거시 경로 역시 새 경로로 연결됩니다.

~~~typescript
// packages/core-types/src/cache.ts
export type * from '@warp-drive/core/types/cache';
~~~

이 세 파일은 핵심 구현 전체를 보여주는 코드가 아니라, 기존 import 경로와 새 패키지 경로 사이의 호환 계층을 보여주는 예시입니다. 따라서 이 파일만으로 내부 캐시 알고리즘이나 반응성 구현 방식까지 추론해서는 안 됩니다.

## 도입 시 확인할 점

- 현재 애플리케이션의 프레임워크 버전이 선택한 WarpDrive 릴리스의 호환 범위에 포함되는지 확인합니다.
- 기존 Ember Data 코드를 옮기는 경우, 사용 중인 import 경로가 레거시 호환 경로인지 확인하고 마이그레이션 안내를 따릅니다.
- JSON:API 어댑터가 필요한 경우 실제 API 스키마와 어댑터 버전의 지원 범위를 확인합니다.
- SSR 환경이라면 서버와 브라우저 사이의 데이터 로딩 및 캐시 수명주기를 실제 앱 구조에서 검증합니다.

## 라이선스와 적합한 사용 사례

저장소의 LICENSE.md는 MIT 라이선스를 명시합니다. 일반적인 MIT 라이선스 조건에 따라 저작권 및 라이선스 고지를 유지하는 범위에서 상업적 사용과 수정, 재배포가 가능합니다.

WarpDrive는 서버 데이터의 모델링과 캐시를 체계적으로 관리하고 싶은 웹 애플리케이션에서 검토할 만합니다. 반면 단순한 UI 상태 관리만 필요하거나, 현재 프레임워크와의 호환성을 확인하지 않은 상태라면 기존 상태 관리 도구와 역할을 먼저 비교하는 편이 좋습니다. Redux나 Zustand와는 해결하려는 문제가 완전히 같지 않으므로, 단순히 기능 수나 번들 크기만으로 우열을 판단하지 않는 것이 안전합니다.
