## 한눈에 보는 프로젝트와 해결하려는 문제

`runelite/plugin-hub`는 오픈소스 게임 클라이언트인 RuneLite에서 공식적으로 지원하지 않는 외부 플러그인들을 체계적으로 관리하기 위한 메타데이터 저장소입니다. 이 프로젝트는 개별 개발자가 만든 플러그인을 사용자가 RuneLite 클라이언트 내부에서 검색하고 설치할 수 있도록 연결하는 '플러그인 마켓플레이스'의 인덱스 역할을 수행합니다.

RuneLite와 같은 확장 가능한 클라이언트는 사용자 커뮤니티가 활발할수록 다양한 기능이 파편화되는 문제를 겪습니다. 본 저장소는 이러한 파편화를 방지하고, 플러그인 개발자가 자신의 코드를 배포할 수 있는 표준화된 절차를 제공합니다. 결과적으로 사용자는 클라이언트 내부에서 외부 플러그인을 안전하게 탐색하고 설치할 수 있는 환경을 제공받습니다.

## 이해에 필요한 핵심 개념

이 프로젝트를 이해하기 위해서는 다음의 두 가지 개념이 필수적입니다.

1. **매니페스트 기반 배포**: 이 저장소는 실제 플러그인 소스 코드를 모두 포함하지 않습니다. 대신, 각 플러그인의 위치(GitHub 저장소 URL)와 특정 버전(커밋 해시)을 명시한 매니페스트 파일들을 `plugins/` 디렉토리에서 관리합니다.
2. **공급망 보안(Supply Chain Security)**: 외부 플러그인은 의존성 라이브러리를 포함할 수 있습니다. 이를 관리하기 위해 Gradle의 의존성 검증 기능을 활용합니다. `package/verification-template/` 내의 설정을 통해 빌드 과정에서 예상치 못한 외부 라이브러리가 포함되는 것을 방지하고 빌드 재현성을 확보합니다.

## 저장소 구조와 실제 동작 흐름

저장소는 크게 플러그인 메타데이터와 개발 도구로 나뉩니다.

* `plugins/`: 각 플러그인의 메타데이터 파일이 위치한 핵심 디렉토리입니다. 예를 들어 `plugins/117hd`와 같은 파일에는 해당 플러그인의 원본 저장소 주소와 빌드에 사용할 커밋 해시가 담겨 있습니다.
* `package/verification-template/`: 새로운 플러그인을 개발하거나 제출할 때 사용하는 템플릿입니다. 여기에는 `build.gradle`과 Gradle Wrapper가 포함되어 있어, 개발자가 로컬 환경에서 플러그인을 빌드하고 테스트할 수 있는 표준 환경을 제공합니다.
* `.github/workflows/`: CI/CD 파이프라인이 정의되어 있습니다. `build.yml`은 제출된 플러그인이 정상적으로 빌드되는지 자동으로 검증합니다.

동작 흐름은 다음과 같습니다: 개발자가 자신의 플러그인을 `plugins/` 디렉토리에 등록하는 Pull Request를 생성하면, GitHub Actions가 이를 빌드하고 검증합니다. 통과 시 메인 브랜치에 병합되며, 이후 RuneLite 클라이언트가 이 저장소의 정보를 참조하여 사용자에게 플러그인 목록을 업데이트해 보여줍니다.

## 구체적인 예제로 보는 설계 선택

플러그인 제출 과정에서 `runelite-plugin.properties` 파일의 역할은 매우 중요합니다.

```
properties
displayName=Helmet check
author=dekvall
description=Alerts you when you have nothing equipped in your head slot
tags=hint,gear,head
plugins=com.helmetcheck.HelmetCheckPlugin
version=
build=standard
```

이 설정 파일은 클라이언트가 플러그인을 UI에 표시할 때 필요한 정보를 담고 있습니다. 특히 `build` 속성은 `standard` 또는 `gradle`로 설정할 수 있습니다. `standard` 모드는 플러그인 제출 시 빌드 환경을 표준화하여 관리하며, 별도의 복잡한 의존성 설정이 필요 없는 경우에 사용됩니다.

## 대안과 비교했을 때의 장단점

플러그인 배포 방식에서 본 프로젝트는 다음과 같은 특징을 가집니다.

* **중앙 집중식 관리 vs 분산형 배포**: 개별 개발자가 각자의 웹사이트에서 플러그인을 배포하는 방식과 비교할 때, 본 프로젝트는 모든 플러그인을 한곳에서 관리하므로 사용자의 검색 편의성이 높습니다. 다만, 모든 변경 사항이 Pull Request를 통해 관리되므로 배포 주기가 중앙 저장소의 검토 속도에 의존합니다.
* **표준화된 빌드 vs 자율 배포**: 사용자가 임의의 `.jar` 파일을 다운로드하여 설치하는 방식은 보안 위험이 큽니다. 반면, 본 저장소는 소스 코드 기반의 빌드와 검증 과정을 거치므로 상대적으로 안전한 배포 환경을 제공합니다.

## 보안·라이선스·도입 시 확인할 점

* **보안**: `README.md`에 명시된 바와 같이, 모든 플러그인은 '있는 그대로(as is)' 제공되며, 프로젝트 관리자는 플러그인의 기능이나 안전성을 보장하지 않습니다. 사용자는 외부 플러그인 설치 시 발생할 수 있는 위험을 스스로 인지해야 합니다.
* **라이선스**: 프로젝트 전체는 `BSD-2-Clause` 라이선스를 따릅니다. 이는 수정 및 재배포가 자유로운 허용적인 라이선스입니다.
* **도입 시 확인**: 새로운 의존성을 추가할 경우 Gradle의 의존성 검증 메타데이터를 업데이트해야 하며, 이는 관리자의 확인 과정을 거칩니다. 따라서 외부 라이브러리 의존성을 최소화하는 것이 원활한 등록에 유리합니다.

## 한계와 추천 대상

본 프로젝트는 RuneLite 생태계 내에서 플러그인을 배포하려는 개발자에게 필수적인 관문입니다. 하지만 다음과 같은 한계가 있습니다.

* **수동 검토 의존**: 모든 플러그인은 관리자의 검토를 거치므로, 즉각적인 배포가 필요한 서비스에는 적합하지 않습니다.
* **클라이언트 종속성**: RuneLite의 클라이언트 API에 종속적이므로, 클라이언트 업데이트 시 플러그인도 함께 수정해야 할 가능성이 높습니다.

추천 대상은 RuneLite 사용자를 위한 유용한 기능을 개발하고 이를 커뮤니티에 공유하고자 하는 개발자입니다. 개인적인 용도의 플러그인이라면 로컬 빌드만으로 충분하며, 본 저장소에 등록할 필요는 없습니다.
