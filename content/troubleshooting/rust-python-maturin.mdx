## 한눈에 보는 프로젝트와 해결하려는 문제

Maturin은 Rust 생태계의 성능과 Python의 유연성을 결합하고자 하는 개발자를 위한 빌드 도구입니다. 과거 `pyo3-pack`이라는 이름으로 시작된 이 프로젝트는, Rust로 작성된 코드를 Python에서 호출할 수 있는 확장 모듈(Wheel)로 변환하는 과정을 자동화합니다.

Python 패키지 배포 표준인 PEP 517/518을 준수하며, `pyo3`, `cffi`, `uniffi`와 같은 다양한 바인딩 방식을 지원합니다. 특히 복잡한 빌드 설정 없이 `maturin build` 명령만으로 플랫폼별 최적화된 바이너리를 생성하고, `manylinux`와 같은 배포 환경 규격을 준수하도록 돕는 것이 핵심 목표입니다.

## 이해에 필요한 핵심 개념

Maturin을 이해하기 위해서는 다음 세 가지 개념이 중요합니다.

1. **Wheel 빌드 및 배포**: Python의 표준 바이너리 배포 형식인 `.whl` 파일을 생성합니다. Maturin은 Rust 컴파일러(`cargo`)를 호출하여 네이티브 코드를 빌드한 뒤, 이를 Python이 인식할 수 있는 구조로 패키징합니다.
2. **바인딩(Bindings)**: Rust와 Python 사이의 데이터 타입 변환 및 함수 호출을 중재하는 계층입니다. `pyo3`는 Rust와 Python 간의 깊은 통합을, `cffi`는 C 호환 인터페이스를, `uniffi`는 다중 언어 지원을 위한 인터페이스를 제공합니다.
3. **Manylinux/Auditwheel**: 리눅스 환경에서 다양한 배포판 간의 호환성을 보장하기 위한 정책입니다. Maturin은 빌드된 라이브러리가 시스템 라이브러리에 과도하게 의존하지 않는지 검사하고, 필요한 경우 라이브러리를 패키지 내부에 포함(repair)하는 기능을 수행합니다.

## 저장소 구조와 실제 동작 흐름

저장소는 크게 CLI 인터페이스, 빌드 로직, 그리고 배포를 위한 보조 도구로 나뉩니다.

* `src/main.rs`: CLI 엔트리 포인트입니다. 사용자의 명령을 파싱하고 `maturin`의 핵심 기능을 호출합니다. `setup_panic_hook` 함수를 통해 릴리스 빌드 시 패닉 발생 상황에서 사용자에게 에러 보고를 요청하는 디버깅 지원 로직을 포함하고 있습니다.
* `src/commands/`: `build`, `develop`, `generate_stubs` 등 사용자가 직접 사용하는 명령어들의 구현체가 위치합니다. 예를 들어 `generate_stubs.rs`는 빌드 과정에서 생성된 메타데이터를 바탕으로 Python 타입 힌트 파일(`.pyi`)을 생성하는 로직을 담당합니다.
* `src/auditwheel/`: 리눅스 환경에서 생성된 Wheel 파일이 배포 규격을 준수하는지 검사하고 수정하는 모듈입니다. `audit.rs`와 `repair.rs`는 라이브러리 의존성을 분석하여 배포 가능한 상태로 만드는 핵심 역할을 합니다.

사용자가 `maturin build`를 실행하면, 프로젝트의 `Cargo.toml`과 `pyproject.toml`을 읽어 빌드 환경을 구성하고, Rust 컴파일을 수행한 뒤, 결과물을 Python Wheel 표준에 맞춰 압축하는 흐름으로 동작합니다.

## 구체적인 예제로 보는 설계 선택

`pyproject.toml` 파일의 `backend-path = ["maturin"]` 설정은 이 도구의 설계 철학을 보여주는 중요한 사례입니다.

```toml
[build-system]
requires = [
    "setuptools>=77.0.0",
    "tomli>=1.1.0 ; python_version<'3.11'",
    "setuptools-rust>=1.11.0",
]
backend-path = ["maturin"]
build-backend = "bootstrap"
```

이 설정은 일반적인 의존성 제거를 위한 것이 아니라, `manylinux`와 같이 특정 빌드 환경에서 Maturin 자체를 부트스트랩하기 위한 우회책(Workaround)으로 사용됩니다. 이는 도구가 스스로를 빌드하거나, 복잡한 환경에서 빌드 백엔드로서 안정적으로 동작해야 하는 요구사항을 반영한 설계입니다.

또한, `test-crates/pyo3-bin/src/main.rs` 예제는 Rust 바이너리가 Python 인터프리터를 내장하여 실행되는 방식을 보여줍니다. `Python::attach`를 통해 Rust 코드 내부에서 Python의 `builtins` 모듈을 호출하는 구조는 Maturin이 단순 라이브러리뿐만 아니라 Python 환경을 포함한 실행 파일 배포까지 고려하고 있음을 시사합니다.

## 대안과 비교했을 때의 장단점

가장 직접적인 대안은 `setuptools-rust`입니다.

* **Maturin**: Rust 프로젝트에 특화되어 있으며, 설정이 매우 간결합니다. `maturin new`를 통해 즉시 프로젝트 구조를 생성할 수 있고, `manylinux` 대응이 내장되어 있어 별도의 복잡한 설정 없이도 배포 준비가 가능합니다.
* **setuptools-rust**: 기존 Python 프로젝트 구조를 유지하면서 Rust를 추가할 때 유리합니다. 하지만 `setuptools`의 복잡한 설정을 그대로 따라야 하므로, 순수 Rust 프로젝트를 Python 패키지로 만들 때는 Maturin보다 설정 부담이 큽니다.

Maturin은 Rust 개발자 경험(DX)에 최적화되어 있으나, 복잡한 Python 빌드 파이프라인(예: C/C++ 확장과 혼합된 경우)에서는 설정의 유연성이 `setuptools`보다 제한적일 수 있습니다.

## 보안·라이선스·도입 시 확인할 점

* **라이선스**: Maturin은 `MIT` 또는 `Apache-2.0` 라이선스 중 하나를 선택하여 사용할 수 있는 이중 라이선스(Dual License) 정책을 채택하고 있습니다. 이는 사용자가 자신의 프로젝트 성격에 맞춰 라이선스를 선택할 수 있는 유연성을 제공합니다.
* **보안 및 안정성**: `src/main.rs`에 구현된 패닉 훅은 릴리스 빌드 시 예기치 못한 오류 발생 시 사용자에게 백트레이스 정보를 제공하여 버그 리포트를 용이하게 합니다. 이는 도구의 안정성을 높이는 것이 아니라, 에러 발생 시 디버깅을 지원하여 개발자가 문제를 빠르게 파악하도록 돕는 기능입니다.
* **도입 시 고려사항**: Maturin은 지속적으로 업데이트되는 도구이므로, `Cargo.toml`의 `rust-version`과 호환되는지 확인해야 합니다. 또한 `manylinux` 정책은 배포 환경에 따라 달라질 수 있으므로, CI/CD 파이프라인에서 `auditwheel`의 동작을 사전에 테스트하는 것이 권장됩니다.

## 한계와 추천 대상

Maturin은 Rust로 Python 확장 모듈을 개발하는 개인 개발자나 소규모 팀에게 가장 적합합니다. 특히 복잡한 빌드 스크립트 작성에 시간을 쏟고 싶지 않은 사용자에게 강력한 생산성을 제공합니다.

반면, Python의 복잡한 빌드 환경(예: 다양한 C 라이브러리 의존성, 복잡한 빌드 시간 환경 변수 설정 등)이 필요한 대규모 프로젝트에서는 Maturin의 자동화된 빌드 방식이 오히려 제약이 될 수 있습니다. 도입 전, 프로젝트가 Maturin의 표준 빌드 흐름 내에서 해결 가능한 수준인지 `guide/` 문서를 통해 확인하는 것을 추천합니다.
