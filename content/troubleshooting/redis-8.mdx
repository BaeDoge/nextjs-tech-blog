## 한눈에 보는 프로젝트와 해결하려는 문제

**프로젝트 유형:** 인메모리 데이터 구조 서버, 캐싱 엔진, 문서 및 벡터 쿼리 엔진 (실제 실행 가능한 바이너리 및 라이브러리)

Redis는 실시간 데이터 기반 애플리케이션을 위한 핵심 인프라로, 단순한 키-값 저장소를 넘어 다양한 데이터 구조(String, Hash, List, Set, Sorted Set 등)와 JSON, 벡터 검색 등의 고급 처리 엔진을 제공합니다. 이 프로젝트는 높은 처리량과 낮은 지연 시간을 요구하는 캐싱, 세션 저장, 메시지 브로커, 그리고 최근에는 AI 애플리케이션을 위한 벡터 데이터베이스로서의 역할을 해결합니다.

저장소 `redis/redis`는 Redis의 핵심 서버 엔진과 이를 빌드하기 위한 의존성 라이브러리, 그리고 동적 로딩을 위한 모듈 개발 환경이 통합되어 있습니다. 8.0 버전부터 라이선스 모델이 변경되었으며, 빌드 시스템과 아키텍처가 현대화되는 과정을 보여줍니다.

## 이해에 필요한 핵심 개념

Redis의 동작과 저장소 구조를 이해하기 위해 다음 세 가지 개념이 중요합니다.

1.  **의존성 라이브러리 (`deps/`) vs 동적 모듈 (`modules/`)**
    저장소 루트의 `deps/` 디렉토리는 Redis 핵심 엔진을 빌드하기 위해 정적으로 링크되거나 포함되는 필수 의존성 라이브러리입니다. 여기에는 메모리 할당자(`jemalloc`), Lua 스크립트 엔진(`lua`), 정적 분석용 라이브러리(`croaring`, `hdr_histogram`) 등이 포함됩니다. 반면, `modules/` 디렉토리는 Redis 서버가 실행 중인 시점에 동적으로 로드(`dlopen`)되어 기능을 확장할 수 있는 API와 예제 코드를 제공합니다. 이 둘은 빌드 시점과 실행 시점의 결합 방식에서 근본적으로 다릅니다.

2.  **삼중 라이선스 모델 (Tri-licensing)**
    Redis 8.0부터는 기존 BSD 3-Clause 라이선스 대신 `RSALv2`, `SSPLv1`, `AGPLv3` 중 하나를 선택하는 삼중 라이선스 모델을 채택했습니다([LICENSE.txt](https://github.com/redis/redis/blob/unstable/LICENSE.txt)). 이는 Redis Ltd.가 기업용 기능(클러스터링, 보안 등)을 오픈소스 라이선스로부터 분리하려는 전략의 일환으로, 신규 기여 코드는 이 라이선스 하에 기여해야 합니다([CONTRIBUTING.md](https://github.com/redis/redis/blob/unstable/CONTRIBUTING.md)).

3.  **확장 가능한 데이터 처리 엔진**
    Redis는 단순 키-값 저장소를 넘어, JSON 문서 처리, 시계열 데이터, 그리고 벡터 검색(Vector Search)을 위한 전용 엔진을 내장하거나 모듈로 제공합니다. 이는 `redis.conf` 설정과 함께 빌드 시 모듈 구성이 결정되며, `redis-full.conf`와 같은 설정 파일을 통해 활성화됩니다([README.md](https://github.com/redis/redis/blob/unstable/README.md)).

## 저장소 구조와 실제 동작 흐름

저장소 트리를 분석하면 Redis의 빌드 및 실행 구조가 명확해집니다.

*   **`src/`**: Redis 서버(`redis-server`), CLI(`redis-cli`), 성능 테스트 도구(`redis-benchmark`) 등의 핵심 소스 코드가 위치합니다.
*   **`deps/`**: 빌드 시 필요한 의존성 라이브러리가 포함됩니다.
    *   `deps/jemalloc/`: 메모리 할당자 소스. Redis는 Linux에서 기본적으로 `jemalloc`을 사용하며, 이는 `libc malloc`보다 단편화 문제가 적습니다([README.md](https://github.com/redis/redis/blob/unstable/README.md)).
    *   `deps/lua/`: Lua 스크립트 엔진. Redis는 Lua를 사용하여 스크립트 실행 및 복잡한 데이터 처리를 지원합니다.
    *   `deps/croaring/`: Roaring Bitmap 구현체. 집합 연산 성능 향상을 위해 사용됩니다.
    *   `deps/hiredis/`: **참고:** 제공된 파일 트리에는 `deps/hiredis`가 포함되어 있지 않습니다. `hiredis`는 Redis 공식 클라이언트 라이브러리이지만, 핵심 저장소의 `deps/` 디렉토리에는 포함되지 않으며 별도의 저장소 또는 시스템 패키지로 관리됩니다. 따라서 `deps/`는 핵심 서버 빌드에만 필요한 라이브러리를 포함한다고 보는 것이 정확합니다.
*   **`modules/`**: 동적 모듈 개발을 위한 API와 예제. 여기에는 벡터 검색을 위한 `vector-sets` 예제가 포함되어 있습니다.
*   **`.github/workflows/`**: CI/CD 파이프라인 정의. `ci.yml`, `codecov.yml` 등이 포함되어 빌드 및 테스트를 자동화합니다.

**동작 흐름:**
1.  **빌드**: `make` 명령어를 실행하면 `deps/`의 의존성 라이브러리가 컴파일되고, `src/`의 코드가 링크되어 `redis-server` 바이너리가 생성됩니다. Redis 8.10 이상에서는 LLVM 21, CMake 3.25–3.31.6, Rust 1.94 등의 도구가 필요합니다([README.md](https://github.com/redis/redis/blob/unstable/README.md)).
2.  **실행**: `redis-server redis.conf` (또는 `redis-full.conf`) 명령어로 서버를 시작합니다. 설정 파일에 따라 JSON, 벡터 검색 등의 엔진이 활성화됩니다.
3.  **모듈 로드**: `MODULE LOAD` 명령어를 통해 `modules/` 디렉토리에서 빌드된 `.so` 파일을 동적으로 로드하여 기능을 확장할 수 있습니다.

## 구체적인 예제로 보는 설계 선택

Redis의 설계 선택 중 하나는 **Lua 스크립트 엔진의 통합**과 **벡터 검색 모듈의 예제**입니다.

**1. Lua 스크립트 엔진의 통합**
Redis는 `deps/lua/`에 Lua 5.4 엔진을 포함하여, 서버 내에서 Lua 스크립트를 실행할 수 있게 합니다. 이는 복잡한 로직을 클라이언트-서버 왕복 없이 서버에서 처리할 수 있게 해줍니다.

`deps/lua/src/lapi.c`의 `lua_pcall` 함수는 Lua 스크립트 실행의 보호된 호출을 보여줍니다.

```c
LUA_API int lua_pcall (lua_State *L, int nargs, int nresults, int errfunc) {
  struct CallS c;
  int status;
  // ... (생략)
  status = luaD_pcall(L, f_call, &c, savestack(L, L->top), 0);
  // ... (생략)
  return status;
}
```

이 코드는 Lua 함수 호출 시 에러 처리를 위한 스택 관리와 보호된 호출(`luaD_pcall`)을 수행합니다. 이는 Redis가 Lua 스크립트 실행 중 예외가 발생해도 서버가 중단되지 않도록 설계되었음을 시사합니다. 또한 `lua_isreadonlytable`과 같은 함수는 Redis가 Lua 테이블의 읽기 전용 속성을 제어할 수 있음을 보여주며, 이는 Redis 데이터 구조와 Lua 간의 안전한 상호작용을 위한 설계 선택입니다.

**2. 벡터 검색 모듈의 CLI 도구**
`modules/vector-sets/examples/cli-tool/README.md`는 벡터 검색 모듈을 위한 CLI 도구의 예제를 제공합니다. 이 도구는 `redis-cli`와 유사하지만, `!"foo bar"` 형식의 인자를 받아 Ollama를 호출하여 임베딩을 생성하고 Redis에 쿼리합니다.

```
markdown
Example:

    redis> KEYS *
    1) food_items
    2) glove_embeddings_bin
    ...

    redis> vsim food_items !"barilla"
    1) Pasta&Noodles,Spirelli,100g,367 cal,1541 kJ
    2) Pasta&Noodles,Farfalle,100g,358 cal,1504 kJ
    ...
```

이 예제는 Redis가 벡터 검색을 위해 외부 임베딩 서비스(Ollama)와 통합될 수 있음을 보여줍니다. `vsim` 명령어는 벡터 유사도 검색을 수행하며, `!"barilla"`와 같은 인자는 텍스트를 임베딩으로 변환하여 검색에 사용합니다. 이는 Redis가 AI 애플리케이션을 위한 유연한 확장을 지원한다는 점을 보여줍니다.

## 대안과 비교했을 때의 장단점

Redis를 대체할 수 있는 주요 인메모리 데이터 저장소인 **Memcached**와 비교합니다.

| 특징 | Redis | Memcached |
| :--- | :--- | :--- |
| **데이터 구조** | String, Hash, List, Set, Sorted Set, JSON, Vector 등 다양함 | String (Key-Value)만 지원 |
| **지속성** | RDB, AOF 등을 통한 디스크 저장 지원 | 지속성 없음 (메모리만 사용) |
| **확장성** | 클러스터링, 샤딩 지원 (Enterprise 기능 포함) | 단순한 샤딩 지원 |
| **라이선스** | RSALv2/SSPLv1/AGPLv3 (8.0+) | BSD 3-Clause |
| **사용 사례** | 캐싱, 세션 저장, 메시지 브로커, 벡터 검색 등 다양함 | 단순 캐싱에 특화 |

**장점:**
*   **다양한 데이터 구조:** Redis는 다양한 데이터 구조를 제공하여 복잡한 데이터 처리를 가능하게 합니다.
*   **지속성:** 디스크 저장을 통해 데이터 손실을 방지할 수 있습니다.
*   **확장성:** 클러스터링을 통해 대규모 데이터 처리가 가능합니다.

**단점:**
*   **라이선스 복잡성:** 8.0부터의 삼중 라이선스는 기업 사용 시 라이선스 준수에 주의가 필요합니다.
*   **단일 스레드 모델 (기본):** 기본 설정에서는 단일 스레드로 동작하여, 높은 동시성 요청 처리에 한계가 있을 수 있습니다. (다만, Redis 7.0부터 멀티스레드 I/O가 도입되었습니다.)

## 보안·라이선스·도입 시 확인할 점

**1. 라이선스**
Redis 8.0부터는 `RSALv2`, `SSPLv1`, `AGPLv3` 중 하나의 라이선스를 선택해야 합니다([LICENSE.txt](https://github.com/redis/redis/blob/unstable/LICENSE.txt)). 기존 코드(7.2 이하)는 BSD 3-Clause를 따릅니다. 신규 기여 코드는 삼중 라이선스 하에 기여해야 하며([CONTRIBUTING.md](https://github.com/redis/redis/blob/unstable/CONTRIBUTING.md)), 기업 사용 시 라이선스 선택에 신중해야 합니다.

**2. 보안**
`SECURITY.md`는 최신 버전 사용을 권장하며, 보안 취약점은 Redis Vulnerability Disclosure Program을 통해 보고해야 한다고 명시합니다([SECURITY.md](https://github.com/redis/redis/blob/unstable/SECURITY.md)). 지원 버전 표에 따르면, 8.10.x, 8.8.x, 8.6.x, 8.4.x, 8.2.x가 지원되며, 8.0.x는 지원되지 않습니다. 7.4.x와 7.2.x의 지원 여부는 제공된 원문 발췌에서 명확히 확인되지 않으므로 단정할 수 없습니다.

**3. TLS**
`TLS.md` 파일이 존재하여 TLS 지원을 언급하고 있지만, 구체적인 설정 방법이나 지원 프로토콜 버전은 제공된 원문에서 확인되지 않습니다. 운영 환경에서는 TLS 설정을 검토해야 하며, `TLS.md`의 내용을 직접 확인하는 것이 좋습니다.

**4. 도입 시 확인할 점**
*   **라이선스 준수:** 삼중 라이선스 중 하나를 선택하여 사용해야 하므로, 기업 정책과 부합하는지 확인해야 합니다.
*   **보안 설정:** TLS, 인증, 권한 설정 등을 운영 환경에 맞게 구성해야 합니다.
*   **성능 튜닝:** 메모리 사용량, 지속성 설정, 클러스터링 구성 등을 애플리케이션 요구사항에 맞게 튜닝해야 합니다.

## 한계와 추천 대상

**한계:**
*   **메모리 사용:** 인메모리 저장소이므로, 데이터 크기가 메모리 용량을 초과할 경우 성능 저하 또는 오류가 발생할 수 있습니다.
*   **라이선스 복잡성:** 8.0부터의 삼중 라이선스는 오픈소스 커뮤니티와 기업 간 라이선스 준수에 혼란을 줄 수 있습니다.
*   **단일 스레드 모델 (기본):** 기본 설정에서는 단일 스레드로 동작하여, 높은 동시성 요청 처리에 한계가 있을 수 있습니다.

**추천 대상:**
*   **실시간 데이터 기반 애플리케이션 개발자:** 높은 처리량과 낮은 지연 시간이 필요한 애플리케이션을 개발하는 경우.
*   **캐싱 솔루션이 필요한 팀:** 세션 저장, API 응답 캐싱 등에 Redis를 활용할 수 있습니다.
*   **벡터 검색이 필요한 AI 애플리케이션 개발자:** Redis의 벡터 검색 모듈을 사용하여 AI 애플리케이션에 검색 기능을 추가할 수 있습니다.
*   **다양한 데이터 구조가 필요한 팀:** String, Hash, List, Set 등 다양한 데이터 구조를 사용하여 복잡한 데이터 처리를 수행해야 하는 경우.

**비추천 대상:**
*   **대용량 영구 저장소가 필요한 경우:** Redis는 인메모리 저장소이므로, 대용량 영구 저장소로는 적합하지 않습니다.
*   **라이선스 준수에 제약이 있는 기업:** 삼중 라이선스 모델이 기업 정책과 부합하지 않는 경우.
