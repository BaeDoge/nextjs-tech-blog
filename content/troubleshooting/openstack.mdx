## 한눈에 보는 프로젝트와 해결하려는 문제

`openstack/openstack` 저장소는 수많은 독립적인 프로젝트로 구성된 OpenStack 생태계의 전체 상태를 동기화하기 위한 '슈퍼 프로젝트(Super-project)' 역할을 수행합니다. OpenStack은 컴퓨팅, 네트워킹, 스토리지 등 다양한 기능을 제공하는 수십 개의 개별 컴포넌트로 나뉘어 개발되는데, 이들 사이의 상호 운용성을 보장하는 것은 매우 복잡한 과제입니다.

이 저장소는 개별 컴포넌트의 소스 코드를 직접 포함하지 않습니다. 대신, `git submodule` 기능을 활용하여 각 컴포넌트의 특정 커밋 해시를 가리키는 포인터들의 집합으로 구성됩니다. 이를 통해 개발자와 운영자는 특정 시점에 Zuul CI 시스템을 통해 함께 테스트되고 검증된 컴포넌트들의 조합을 명확하게 식별할 수 있습니다. 즉, 이 프로젝트는 코드 저장소가 아니라, 거대한 분산 시스템의 '버전 스냅샷'을 관리하는 도구입니다.

## 이해에 필요한 핵심 개념

이 프로젝트를 이해하기 위해서는 다음 두 가지 개념이 필수적입니다.

1. **Git 서브모듈(Submodules):** Git 저장소 안에 다른 Git 저장소를 하위 디렉토리로 포함하는 기능입니다. 이 저장소는 각 컴포넌트를 서브모듈로 등록하여, 특정 시점의 전체 OpenStack 상태를 하나의 커밋으로 고정(Pinning)합니다.
2. **Zuul CI 게이팅(Gating):** OpenStack의 지속적 통합 시스템인 Zuul은 여러 저장소에 걸친 변경 사항이 서로 충돌하지 않는지 확인합니다. 이 저장소는 Zuul이 검증을 마친 '성공적인 조합'을 기록하는 최종 목적지 역할을 수행합니다.

## 저장소 구조와 실제 동작 흐름

이 저장소는 사람이 직접 코드를 수정하는 곳이 아니라, 자동화된 스크립트에 의해 상태가 갱신되는 구조를 가집니다.

* `.gitmodules`: 각 컴포넌트의 경로와 원격 저장소 URL을 정의합니다.
* `generate-gitmodules.py`: OpenStack 거버넌스 데이터(`projects.yaml`)를 참조하여 서브모듈 목록을 동적으로 생성하는 자동화 스크립트입니다.
* `README.rst`: 프로젝트의 목적과 사용법을 설명하는 문서입니다.

동작 흐름은 다음과 같습니다:
1. `generate-gitmodules.py`가 실행되어 `opendev.org`의 프로젝트 정보를 가져옵니다.
2. 스크립트는 현재 포함된 서브모듈과 최신 프로젝트 목록을 대조합니다.
3. 새로운 프로젝트가 추가되거나 삭제되면 `git submodule add` 또는 `git rm` 명령을 통해 저장소 구조를 업데이트합니다.
4. 최종적으로 `.gitmodules` 파일이 갱신되어 전체 시스템의 구성을 반영합니다.

```python
# generate-gitmodules.py의 핵심 로직 예시
def find_integrated_gate_repos():
    r = requests.get(CONFIG)
    projects = yaml.safe_load(r.text)
    repos = []
    for project in projects.values():
        for deliverable in project.get('deliverables', {}).values():
            for repo in deliverable['repos']:
                repos.append(repo)
    return repos
```

## 구체적인 예제로 보는 설계 선택

이 저장소의 설계는 '읽기 전용(Read-only)' 원칙을 고수합니다. 이는 개발자가 개별 컴포넌트를 수정할 때 이 저장소에 커밋하는 것이 아니라, 각 컴포넌트의 고유 저장소에서 작업해야 함을 의미합니다.

`generate-gitmodules.py`의 `TEMPLATE` 변수를 보면, 서브모듈이 어떤 방식으로 관리되는지 알 수 있습니다.

```python
TEMPLATE = """[submodule "%s"]
\tpath = %s
\turl = ../../%s.git
\tbranch = .
"""
```

이 구조는 `opendev.org`의 상대 경로를 사용하여 저장소 간의 관계를 정의합니다. 이는 특정 인프라 환경에 종속되지 않고, OpenStack의 거버넌스 체계 내에서 프로젝트들이 일관된 구조를 유지하도록 강제합니다.

## 대안과 비교했을 때의 장단점

이 방식은 모노레포(Monorepo)와 대조됩니다.

| 구분 | OpenStack 서브모듈 방식 | 모노레포 방식 |
| :--- | :--- | :--- |
| **결합도** | 낮음 (독립적 개발 가능) | 높음 (전체 빌드 필요) |
| **버전 관리** | 서브모듈 포인터로 관리 | 단일 커밋으로 관리 |
| **복잡도** | 도구 사용 숙련도 필요 | 대규모 저장소 관리 부담 |

**장점:** 각 컴포넌트 팀은 자신들의 저장소에서 독립적으로 개발 속도를 조절할 수 있습니다.
**단점:** 서브모듈의 특성상 `git submodule update --init --recursive`와 같은 명령어를 빈번히 사용해야 하며, 상태 동기화가 깨질 경우 복구 과정이 번거로울 수 있습니다.

## 보안·라이선스·도입 시 확인할 점

* **라이선스:** Apache-2.0 라이선스를 따릅니다. 이는 기업 환경에서 자유롭게 사용하고 수정할 수 있는 허용적인 라이선스입니다.
* **도입 시 주의사항:** 이 저장소는 OpenStack의 전체 구성 상태를 파악하는 용도입니다. 만약 OpenStack을 배포하려는 목적이라면 이 저장소의 코드를 직접 빌드하는 것이 아니라, `openstack.org`에서 제공하는 공식 배포 도구(Kolla, OpenStack-Ansible 등)를 사용하는 것이 권장됩니다.
* **보안:** 이 저장소 자체에는 실행 가능한 코드가 거의 없으므로 직접적인 취약점은 낮습니다. 다만, 서브모듈로 연결된 개별 프로젝트들의 보안 업데이트를 주기적으로 확인해야 합니다.

## 한계와 추천 대상

**한계:**
이 저장소는 '코드 저장소'라기보다 '메타데이터 저장소'에 가깝습니다. 따라서 소스 코드를 수정하거나 기능을 추가하려는 개발자에게는 직접적인 도움이 되지 않습니다.

**추천 대상:**
1. OpenStack 생태계 전체의 프로젝트 구성과 의존 관계를 파악하려는 아키텍트.
2. 특정 OpenStack 릴리스 버전에서 어떤 컴포넌트들이 함께 검증되었는지 확인하려는 시스템 엔지니어.
3. 대규모 분산 시스템의 버전 관리 전략을 연구하는 오픈소스 연구자.

이 프로젝트는 OpenStack이라는 거대한 생태계를 하나의 거버넌스 아래 묶어두는 '지도'와 같은 역할을 합니다. 따라서 프로젝트의 구조를 이해하고 전체적인 흐름을 파악하는 데 활용하는 것이 가장 적합합니다.
