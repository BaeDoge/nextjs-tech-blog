## 한눈에 보는 프로젝트와 해결하려는 문제

TypeSpec은 Microsoft가 주도하고 커뮤니티가 지원하는 오픈소스 프로젝트로, 클라우드 서비스 API와 데이터 구조를 정의하기 위한 **타입 정의 언어(Type Definition Language)**이자 이를 처리하는 **개발 도구 모음**입니다. 이 프로젝트의 성격은 단순한 라이브러리가 아니라, API 설계부터 코드 생성, 문서화까지 이어지는 파이프라인의 핵심 엔진 역할을 하는 '중간 표현(IR)' 도구입니다.

기존의 API 개발 파이프라인에서는 REST API의 경우 OpenAPI(Swagger)를, gRPC의 경우 Protobuf를, GraphQL의 경우 SDL을 각각 다른 형식으로 관리하는 경우가 많습니다. 이는 동일한 비즈니스 로직이 프로토콜마다 중복 정의되어야 하는 '다중 진실 공급원(Multiple Sources of Truth)' 문제를 야기합니다. TypeSpec은 REST, OpenAPI, gRPC, JSON Schema 등 다양한 프로토콜에서 공통적으로 사용되는 API의 형태(Shape)를 추상화하여 단일한 소스 코드로 관리하고, 이를 기반으로 필요한 형식이나 언어별 SDK를 생성하는 것을 목표로 합니다.

주요 사용자층은 Azure와 같은 클라우드 서비스를 설계하는 엔지니어, 그리고 다양한 언어의 SDK를 유지보수해야 하는 개발자입니다. `@typespec/compiler`를 핵심 컴파일러로 하여, `@typespec/http`, `@typespec/rest` 등의 라이브러리를 통해 API 규약을 정의하고, `@typespec/openapi3` 등의 이미터(Emitter)를 통해 최종 산출물을 생성하는 구조를 가집니다.

## 이해에 필요한 핵심 개념

TypeSpec의 동작 원리를 이해하기 위해 다음 세 가지 핵심 개념을 살펴볼 필요가 있습니다.

첫째, **프로토콜 중립적 정의(Protocol-Neutral Definition)**입니다. TypeSpec은 특정 프로토콜(예: HTTP)에 종속되지 않는 기본 타입과 구조를 제공합니다. 예를 들어 `model` 키워드로 데이터 구조를 정의하고, `@route` 데코레이터로 HTTP 경로를 매핑하는 식입니다. 이는 같은 TypeSpec 코드를 통해 REST API용 OpenAPI 문서와 gRPC용 Protobuf 파일을 동시에 생성할 수 있는 기반이 됩니다.

둘째, **Emitter(이미터) 프레임워크**입니다. TypeSpec 코드는 최종 산출물이 아닙니다. TypeSpec 컴파일러는 TypeSpec 코드를 파싱하여 내부 표현(IR)으로 변환한 후, Emitter 패키지에 전달합니다. `@typespec/openapi3` 이미터는 이 IR을 받아 OpenAPI 3.0 JSON 형식으로 변환하고, `@typespec/http-client-java` 이미터는 동일한 IR을 받아 Java SDK 코드를 생성합니다. 이는 TypeSpec이 '변환기'가 아니라 '정의 도구'임을 보여줍니다.

셋째, **확장 가능한 라이브러리 시스템**입니다. TypeSpec은 `@typespec/http`, `@typespec/versioning` 등 도메인별 라이브러리를 통해 기능을 확장합니다. `@typespec/versioning` 라이브러리는 API 버전 관리를 위한 데코레이터와 로직을 제공하며, 사용자가 직접 새로운 데코레이터와 이미터를 작성하여 TypeSpec 언어 자체를 확장할 수도 있습니다. 이는 README에서 언급된 "reusable patterns for all aspects of an API"의 기술적 구현체입니다.

## 저장소 구조와 실제 동작 흐름

TypeSpec 저장소는 단일 애플리케이션이 아니라, `pnpm` 워크스페이스로 관리되는 다중 패키지(Monorepo) 구조를 가집니다. 주요 패키지는 `packages` 디렉토리 하위에 위치하며, 각 패키지는 독립적인 npm 패키지로 배포됩니다.

핵심 패키지의 책임과 흐름은 다음과 같습니다.

1.  **컴파일러 (`@typespec/compiler`)**: TypeSpec 소스 코드(`.tsp` 파일)를 구문 분석하여 AST(구문 트리)와 내부 표현(IR)을 생성합니다. 타입 체크, 린팅, 데코레이터 실행 등의 역할을 수행합니다.
2.  **라이브러리 (`@typespec/http`, `@typespec/rest`, `@typespec/openapi3` 등)**: HTTP, REST, OpenAPI 등 특정 도메인에 대한 데코레이터와 유틸리티를 제공합니다. 이 라이브러리들은 컴파일러에 의해 로드되어 TypeSpec 코드의 의미를 확장합니다.
3.  **이미터 (`@typespec/openapi3`, `@typespec/http-client-java` 등)**: 컴파일러가 생성한 IR을 받아 최종 산출물(OpenAPI JSON, Java 코드 등)을 생성합니다. 특히 Java SDK 생성과 관련된 패키지는 `packages/http-client-java` 하위에 위치하며, 여기서 이미터 로직과 코드 생성기(Generator)가 분리되어 관리됩니다.

실제 동작 흐름은 다음과 같습니다.
1.  사용자가 `main.tsp` 파일에 TypeSpec 코드를 작성합니다.
2.  `tsp compile main.tsp --emit @typespec/openapi3` 명령어를 실행합니다.
3.  컴파일러가 `.tsp` 파일을 파싱하고, `@typespec/http` 등의 라이브러리를 통해 타입과 데코레이터를 해석합니다.
4.  내부 표현(IR)이 생성되면, 지정된 이미터(`@typespec/openapi3`)가 IR을 조회하여 OpenAPI 3.0 형식의 JSON 파일을 생성합니다.

이러한 구조는 `package.json`에서 `@typespec/monorepo`라는 이름으로 관리되며, `turbo`를 사용하여 빌드 의존성을 관리하고 있습니다. Java 클라이언트 생성과 같은 특정 언어 SDK 생성 기능은 `packages/http-client-java` 패키지에 포함되어 있으며, 이 패키지는 이미터와 네이티브 코드 생성기(Generator)를 포함하는 독립적인 모듈로 설계되어 있습니다.

## 구체적인 예제로 보는 설계 선택

TypeSpec의 설계 선택을 이해하기 위해 README에 제시된 기본 예제와 Java SDK 생성 구조를 비교해 살펴보겠습니다.

### 1. README의 기본 예제 (OpenAPI 생성)

README(`README.md`)에는 `@typespec/http`, `@typespec/rest`, `@typespec/openapi3` 라이브러리를 사용한 REST API 정의 예제가 제시되어 있습니다.

```
typespec
import "@typespec/http";
import "@typespec/rest";
import "@typespec/openapi3";

using Http;
using Rest;

/** This is a pet store service. */
@service(#{ title: "Pet Store Service" })
@server("https://example.com", "The service endpoint")
namespace PetStore;

@route("/pets")
interface Pets {
  list(): Pet[];
}

model Pet {
  @minLength(100)
  name: string;

  @minValue(0)
  @maxValue(100)
  age: int32;

  kind: "dog" | "cat" | "fish";
}
```

이 예제는 TypeSpec이 어떻게 직관적인 구문으로 API를 정의하는지 보여줍니다. `model Pet`은 데이터 구조를, `@route("/pets")`는 HTTP 경로를, `@minLength`와 같은 데코레이터는 제약 조건을 정의합니다. 이 코드를 `tsp compile`로 컴파일하면 OpenAPI 3.0 JSON이 생성됩니다. 이는 TypeSpec이 프로토콜 세부 사항(HTTP 메서드, 헤더 등)을 데코레이터를 통해 명시적으로 관리하면서도, 최종 출력물은 표준 형식인 OpenAPI로 변환한다는 설계 선택을 반영합니다.

### 2. Java SDK 생성 구조 (생성된 예제 코드 분석)

Java SDK 생성 기능은 `packages/http-client-java` 패키지에 구현되어 있습니다. 이 패키지의 이미터는 TypeSpec IR을 받아 Java 코드를 생성합니다. 저장소 내 `packages/http-client-java/generator/http-client-generator-test/src/main/java/azure/example/basic/models/Enum.java` 파일은 TypeSpec 컴파일러가 생성한 **생성된 예제 코드(Generated Code)**입니다.

```java
// Copyright (c) Microsoft Corporation. All rights reserved.
// Licensed under the MIT License.
// Code generated by Microsoft (R) TypeSpec Code Generator.

package azure.example.basic.models;

import com.azure.core.annotation.Generated;
import com.azure.core.util.ExpandableStringEnum;
import java.util.Collection;

/**
 * Defines values for Enum.
 */
public final class Enum extends ExpandableStringEnum<Enum> {
    /**
     * Static value EnumValue1 for Enum.
     */
    @Generated
    public static final Enum ENUM_VALUE1 = fromString("EnumValue1");

    // ...
}
```

이 파일의 주석 `Code generated by Microsoft (R) TypeSpec Code Generator.`은 이 코드가 수동으로 작성된 것이 아니라, TypeSpec 정의에서 자동 생성되었음을 명시합니다. 또한 `com.azure.core.util.ExpandableStringEnum`을 상속받아 Azure SDK for Java의 관례에 맞게 Enum을 구현하고 있으며, `@Generated` 어노테이션을 붙여 생성된 코드임을 표시합니다. 이는 TypeSpec이 단순히 코드를 생성하는 것을 넘어, 타겟 언어(여기서는 Java)의 생태계와 관례(Azure SDK for Java의 패턴)를 따르도록 설계되었음을 보여줍니다.

또한 `packages/http-client-java/generator/http-client-generator-core/src/main/java/com/microsoft/typespec/http/client/generator/core/template/example/ModelExampleWriter.java` 파일은 생성된 모델 클래스에 대한 예제 코드와 어설션(Assertion)을 자동으로 생성하는 로직이 포함되어 있습니다. 이는 생성된 SDK가 단위 테스트나 예제 코드와 함께 배포될 때, 일관된 형식의 테스트 케이스를 제공하여 SDK의 신뢰성을 높이는 설계 선택을 반영합니다.

## 대안과 비교했을 때의 장단점

TypeSpec의 주요 대안으로는 OpenAPI(Swagger), Protobuf, 그리고 직접 수동으로 SDK를 작성하는 경우가 있습니다.

| 비교 항목 | TypeSpec | OpenAPI / Protobuf (기존 방식) |
| :--- | :--- | :--- |
| **단일 진실 공급원** | **강점**: 하나의 TypeSpec 코드로 REST, gRPC, JSON Schema 등 다양한 형식 동시 생성 가능 | **약점**: 프로토콜마다 별도 정의 필요, 동기화 어려움 |
| **확장성** | **강점**: 데코레이터와 이미터 프레임워크를 통해 언어와 도메인 확장 용이 | **약점**: 스키마 확장 기능 제한적, 커스텀 로직 적용 어려움 |
| **학습 곡선** | **중간**: 새로운 언어 구문 학습 필요, 하지만 기존 스키마 언어와 유사 | **낮음**: OpenAPI/Protobuf는 널리 알려져 있음 |
| **생태계 통합** | **중간**: Azure SDK 등 일부 생태계에서 적극 활용, 하지만 아직 보편화 단계 | **강점**: 전 세계적으로 광범위한 도구 및 라이브러리 지원 |

TypeSpec의 가장 큰 장점은 **다중 프로토콜 지원**과 **확장성**입니다. 동일한 API를 REST와 gRPC로 동시에 제공해야 하는 경우, TypeSpec을 사용하면 한 번의 정의로 두 가지 형식을 생성할 수 있어 유지보수 비용이 크게 줄어듭니다. 또한, 데코레이터 시스템을 통해 조직 내부의 API 설계 가이드라인(Guardrails)을 코드 레벨에서 강제할 수 있습니다.

반면, 단점은 **생태계의 성숙도**입니다. OpenAPI나 Protobuf는 수십 년간 축적된 도구와 커뮤니티를 가지고 있는 반면, TypeSpec은 비교적 새로운 프로젝트입니다. 따라서 특정 언어나 프레임워크와의 통합이 아직 완벽하지 않을 수 있으며, 학습 비용이 발생할 수 있습니다. 또한, TypeSpec 코드를 직접 작성해야 하므로, 기존 OpenAPI 스키마를 가진 프로젝트에서는 마이그레이션 비용이 발생할 수 있습니다.

## 보안·라이선스·도입 시 확인할 점

### 라이선스
TypeSpec은 **MIT License** 하에 배포됩니다. `LICENSE` 파일에 명시된 바와 같이, 상업적 사용, 수정, 배포, sublicensing가 모두 허용되며, 저작권 고지만 유지하면 됩니다. 이는 기업 환경에서의 도입 장벽을 낮추는 중요한 요소입니다.

### 보안
TypeSpec 저장소는 Microsoft의 일반적인 보안 정책을 따릅니다. `SECURITY.md` 파일은 Microsoft Security Response Center(MSRC)를 통한 보안 취약점 보고 절차를 안내하고 있습니다. 이는 TypeSpec 고유의 보안 정책이라기보다는, Microsoft가 운영하는 모든 오픈소스 저장소에 적용되는 표준 템플릿입니다. 따라서 TypeSpec 자체의 보안 취약점보다는, TypeSpec을 통해 생성된 코드나 사용하는 의존 패키지의 보안 관리가 중요합니다.

### 도입 시 확인할 점
1.  **의존성 관리**: TypeSpec은 `pnpm`을 기본 패키지 매니저로 사용하며, 여러 패키지로 분산되어 있습니다. 도입 시 `package.json`에서 필요한 패키지(`@typespec/compiler`, `@typespec/http` 등)를 정확히 선택해야 합니다.
2.  **생성된 코드의 관리**: TypeSpec은 생성된 코드를 버전 관리에 포함할지 여부를 결정해야 합니다. 일반적으로 생성된 코드는 `.gitignore`에 포함하고, TypeSpec 소스 코드만 관리하는 것이 권장됩니다.
3.  **이미터 선택**: 생성할 타겟 언어와 형식에 맞는 이미터가 존재하는지 확인해야 합니다. Java SDK 생성의 경우 `@typespec/http-client-java` 이미터가 제공되지만, 다른 언어의 경우 추가 개발이 필요할 수 있습니다.

## 한계와 추천 대상

### 한계
1.  **생성된 코드의 커스터마이징 제한**: TypeSpec은 생성된 코드의 구조와 내용을 정의하는 데 중점을 둡니다. 생성된 코드 내부의 비즈니스 로직이나 특정 프레임워크와의 깊은 통합은 TypeSpec만으로 제어하기 어렵습니다. 생성된 코드를 기반으로 추가 수정이 필요할 수 있습니다.
2.  **도구 생태계의 제한**: OpenAPI나 Protobuf에 비해 지원되는 도구(IDE 플러그인, 테스트 도구, 시각화 도구 등)가 아직 제한적입니다. VS Code 확장 프로그램이 제공되지만, 모든 기능이 완벽하게 구현되지는 않을 수 있습니다.
3.  **학습 비용**: 새로운 언어 구문과 개념을 학습해야 하므로, 기존 스키마 언어에 익숙한 개발자에게는 진입 장벽이 될 수 있습니다.

### 추천 대상
TypeSpec은 다음과 같은 경우에 특히 유용합니다.
1.  **다중 프로토콜 API 제공**: REST, gRPC, GraphQL 등 여러 프로토콜을 동시에 지원하는 API를 설계하는 팀.
2.  **대규모 SDK 유지보수**: Java, Python, .NET 등 여러 언어의 SDK를 일관된 방식으로 생성하고 유지보수해야 하는 기업(특히 Azure SDK와 같은 대규모 SDK 생태계).
3.  **API 설계 가이드라인 강제**: 조직 내부의 API 설계 표준을 TypeSpec 데코레이터와 린터 규칙으로 정의하여, 모든 개발자가 이를 따르도록 강제하고 싶은 경우.

반면, 단순한 REST API 하나만 제공하고, SDK 생성이 필요 없으며, 기존 OpenAPI 스키마로 충분하다면 TypeSpec 도입은 오히려 복잡성만 증가시킬 수 있습니다. 이러한 경우 기존 OpenAPI 도구를 사용하는 것이 더 효율적일 수 있습니다.
