## 한눈에 보는 프로젝트와 해결하려는 문제

`PostHog/posthog-foss`는 제품 분석, 세션 리플레이, 기능 플래그, 비즈니스 데이터 수집 및 시각화를 제공하는 PostHog 플랫폼의 오픈소스 전용 미러 저장소입니다. 이 프로젝트는 메인 저장소(posthog)에서 기업용 독점 코드(Proprietary code)를 제거한 상태를 유지하며, 사용자가 데이터 주권을 확보하고 자체 호스팅 환경에서 제품의 컨텍스트 레이어를 구축할 수 있도록 돕는 것을 목표로 합니다.

주요 해결 과제는 데이터 사일로 현상입니다. 파편화된 분석 도구들을 하나로 통합하여, 개발자가 제품 사용자의 행동 데이터를 쿼리하고 즉각적인 수정 사항을 배포할 수 있는 환경을 제공합니다. 이는 단순한 분석 도구를 넘어, 제품의 컨텍스트를 관리하는 플랫폼으로서의 역할을 수행합니다.

## 이해에 필요한 핵심 개념

PostHog를 이해하기 위해서는 다음 두 가지 핵심 개념이 중요합니다.

1. **컨텍스트 레이어(Context Layer):** 단순한 이벤트 로그를 넘어 사용자 세션, 에러, 기능 플래그 상태를 통합하여 제품의 현재 상태와 사용자 경험을 종합적으로 파악하는 개념입니다.
2. **HogQL:** PostHog에서 사용하는 쿼리 언어로, ClickHouse 기반의 강력한 분석 쿼리를 수행합니다. 저장소 내 `package.json`의 `grammar:build` 스크립트 등을 통해 관련 파서 빌드 과정을 확인할 수 있습니다.

## 저장소 구조와 실제 동작 흐름

저장소는 크게 백엔드(Python/Django), 프론트엔드(React/TypeScript), 그리고 인프라 관리 도구로 구성됩니다.

- `products/`: 각 제품 단위의 워크스페이스가 분리되어 관리됩니다. 예를 들어 `products/mobile/`은 모바일 앱 관련 CI 및 빌드 로직을 포함합니다.
- `cli/`: Rust로 작성된 CLI 도구로, `cli/src/main.rs`에서 볼 수 있듯이 원격 API와의 통신, 원격 측정(Telemetry) 초기화, 명령어 처리를 담당합니다.
- `Dockerfile`: 프로덕션 빌드를 위한 다단계 빌드(Multi-stage build)를 수행하며, 노드 기반의 프론트엔드 빌드와 장고(Django) 기반의 백엔드 정적 파일 수집 과정을 포함합니다.

사용자가 시스템을 실행하면 `nodejs/src/server.ts`와 같은 진입점을 통해 Redis, Postgres, Kafka 등 공유 인프라와 연결되며, 각 서비스는 `IntegrationManagerService` 등을 통해 데이터 흐름을 제어합니다.

## 구체적인 예제로 보는 설계 선택

`cli/src/main.rs`의 구현을 보면, CLI 도구가 실행될 때의 초기화 흐름을 확인할 수 있습니다.

```rust
fn main() {
    let subscriber = tracing_subscriber::fmt()
        .with_writer(BrokenPipeSafeStderr)
        .with_env_filter(
            tracing_subscriber::EnvFilter::builder()
                .with_default_directive(tracing::Level::INFO.into())
                .from_env_lossy(),
        )
        .finish();

    tracing::subscriber::set_global_default(subscriber).expect("Failed to set tracing subscriber");
    init_posthog_telemetry();

    let result = cmd::Cli::run();
    posthog_rs::flush();
    // ...
}
```

이 코드는 `tracing` 라이브러리를 사용하여 로깅을 표준화하고, `init_posthog_telemetry`를 통해 원격 측정 기능을 초기화합니다. 특히 `posthog_rs::flush()`를 호출하여 프로세스 종료 전 데이터를 안전하게 전송하는 설계는 분산 환경에서 데이터 유실을 방지하기 위한 전형적인 패턴입니다.

## 대안과 비교했을 때의 장단점

PostHog FOSS는 기존의 상용 분석 도구와 비교했을 때 다음과 같은 특징이 있습니다.

- **장점:** 데이터 소유권이 사용자에게 있으며, 오픈소스 기반으로 커스터마이징이 가능합니다. 특히 ClickHouse를 활용한 고성능 쿼리 처리가 강점입니다.
- **단점:** 자체 호스팅 시 인프라 관리 부담(4GB 이상의 메모리 권장 등)이 큽니다. 또한 상용 버전(Cloud)에서 제공하는 일부 고급 기능은 FOSS 버전에서 제외되어 있을 수 있습니다.

## 보안·라이선스·도입 시 확인할 점

- **라이선스:** MIT 라이선스를 따르며, 이는 상업적 이용을 포함한 넓은 자유도를 제공합니다.
- **보안:** GitHub 저장소에는 `.semgrep`, `.trunk`, `.github/SECURITY.md` 등 보안 관련 파일이 포함되어 있어 보안 정책이 존재함을 알 수 있습니다. 도입 시에는 일반적인 웹 애플리케이션 보안 가이드라인을 준수해야 하며, API 키 관리 및 데이터 접근 제어 설정을 철저히 검토해야 합니다.
- **도입 시:** `README.md`에 명시된 대로, 오픈소스 배포판은 약 10만 이벤트/월 수준의 스케일링이 제한 사항으로 명시되어 있으며, 그 이상의 트래픽 발생 시 PostHog Cloud로의 이전을 고려해야 합니다.

## 한계와 추천 대상

이 프로젝트는 제품 분석을 자체 호스팅 환경에서 완벽하게 제어하고자 하는 엔지니어링 팀에게 적합합니다. 반면, 인프라 운영 리소스가 부족하거나 즉각적인 기술 지원이 필요한 기업에는 적합하지 않을 수 있습니다.

**추천 대상:**
- 데이터 보안 규정상 외부 SaaS 사용이 어려운 기업
- 제품 분석 로직을 직접 수정하거나 확장해야 하는 팀
- ClickHouse 기반의 고성능 데이터 분석 인프라를 구축하려는 개발자

**한계:**
- 상용 클라우드 버전 대비 기능적 제약이 존재할 수 있음
- 자체 호스팅 시 발생하는 운영 비용과 복잡도
- 공식적인 기술 지원이 제공되지 않으므로 커뮤니티와 문서에 의존해야 함
