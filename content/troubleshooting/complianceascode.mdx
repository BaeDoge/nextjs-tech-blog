## 한눈에 보는 프로젝트와 해결하려는 문제

`ComplianceAsCode/content`는 운영체제(RHEL, Fedora, Ubuntu, Debian 등) 및 애플리케이션(Firefox 등)에 대한 보안 정책 콘텐츠를 생성하고 배포하는 프로젝트입니다. 이 프로젝트는 실행 가능한 라이브러리나 프레임워크라기보다, **보안 정책 콘텐츠의 원천 저장소이자 빌드 시스템**으로 분류할 수 있습니다.

기존의 보안 가이드는 각 배포판이나 표준(NIST, STIG, CIS 등)마다 별도 파일로 관리되어 중복이 많고 유지보수가 어려웠습니다. ComplianceAsCode는 "Write once, generate everywhere"라는 목표를 가지고, 보안 규칙을 단일한 YAML 형식으로 정의한 뒤 빌드 시스템을 통해 XCCDF, OVAL, Ansible Playbook, Bash 스크립트 등 다양한 포맷으로 변환하여 제공합니다. 이를 통해 보안 전문가가 한 번의 수정으로 모든 플랫폼과 도구에 적용 가능한 콘텐츠를 유지할 수 있도록 합니다.

## 이해에 필요한 핵심 개념

프로젝트의 동작을 이해하기 위해서는 다음 세 가지 핵심 개념을 파악해야 합니다.

1. **OpenControl 스타일의 YAML 규칙**: 프로젝트의 입력 형식입니다. 보안 요구사항을 `title`, `description`, `severity`, `identifiers` 등의 필드로 구조화하여 저장합니다. 이 YAML 파일은 기계가 읽을 수 있는 원천 데이터입니다.
2. **빌드 시스템 (Build System)**: `CMake`와 `Python` 스크립트를 기반으로 합니다. YAML 규칙을 파싱하여 각 출력 포맷(Ansible, Bash, SCAP 등)에 맞는 템플릿과 결합합니다. `pyproject.toml`에 명시된 대로 `ssg` 라이브러리가 이 빌드 과정의 핵심을 담당합니다.
3. **SCAP 소스 데이터 스트림 (Source Data Stream)**: 최종 출력물 중 하나로, XCCDF, OVAL, CPE 등의 정보를 하나의 XML 파일에 통합한 것입니다. `oscap` 도구 등이 이를 스캔하여 시스템의 준수 여부를 평가합니다.

## 저장소 구조와 실제 동작 흐름

저장소의 구조는 입력 데이터, 빌드 도구, 출력물, 테스트 환경으로 나뉩니다.

*   **입력 데이터 (`rules/`, `products/`)**: 보안 규칙과 대상 플랫폼(예: `rhel9`, `ubuntu2204`)에 대한 메타데이터가 저장됩니다.
*   **빌드 도구 (`build-scripts/`, `ssg/`)**: `build-scripts/cpe_generate.py`와 같은 스크립트는 CPE(Common Platform Enumeration) 정보를 추출하고 정리하는 데 사용됩니다. `ssg/` 폴더에는 YAML을 파싱하고 XML/Ansible 등을 생성하는 Python 라이브러리가 포함되어 있습니다.
*   **출력물 (`build/`)**: 빌드가 완료되면 `build/` 디렉토리에 생성된 파일들이 실제 배포됩니다. 여기에는 `ssg-rhel9-ds.xml`(SCAP 데이터 스트림), `ansible/` 폴더의 플레이북, `bash/` 폴더의 스크립트가 포함됩니다.
*   **테스트 및 CI (`.github/workflows/`)**: `automatus.yaml` 등 다양한 워크플로우가 정의되어 있어, 각 플랫폼별로 규칙의 유효성을 자동으로 검증합니다.

동작 흐름은 다음과 같습니다.
1. 개발자가 `rules/` 하위에 YAML 형식의 보안 규칙을 작성합니다.
2. 빌드 스크립트가 `products/`의 구성을 읽어, 해당 플랫폼에 필요한 규칙을 필터링합니다.
3. `ssg` 라이브러리가 YAML을 파싱하고, Jinja2 템플릿을 적용하여 Ansible, Bash, OVAL 등의 코드를 생성합니다.
4. 최종적으로 SCAP 데이터 스트림과 기타 파일들이 `build/` 디렉토리에 패키징됩니다.

## 구체적인 예제로 보는 설계 선택

`README.md`에 제시된 예제를 통해 YAML 규칙의 구조와 빌드 시스템의 동작을 살펴보겠습니다.

```yaml
title: 'Configure The Number of Allowed Simultaneous Requests'

description: |-
    The <tt>MaxKeepAliveRequests</tt> directive should be set and configured to
    <sub idref="var_max_keepalive_requests" /> or greater by setting the following
    in <tt>/etc/httpd/conf/httpd.conf</tt>:
    <pre>MaxKeepAliveRequests {{{ xccdf_value("var_max_keepalive_requests") }}}</pre>

severity: medium

identifiers:
    cce: "80551-5"
```

이 예제에서 주목할 점은 `description` 필드입니다.
*   **변수 참조**: `<sub idref="var_max_keepalive_requests" />`는 OVAL 등에서 사용되는 변수 참조 형식입니다.
*   **템플릿 구문**: `{{{ xccdf_value("var_max_keepalive_requests") }}}`는 빌드 시스템이 XCCDF 프로필에서 해당 변수의 값을 찾아서 최종 문서(HTML 가이드 등)에 삽입하도록 하는 템플릿 구문입니다.

이 설계의 장점은 **단일 소스 관리**입니다. 개발자는 `MaxKeepAliveRequests`의 설정 값이나 설명을 한 곳(YAML)에서만 수정하면 됩니다. 빌드 시스템은 이를 파싱하여:
*   **OVAL**: 변수 값을 비교하는 테스트 로직을 생성합니다.
*   **Ansible**: `var_max_keepalive_requests` 값을 사용하여 `httpd.conf`를 수정하는 태스크를 생성합니다.
*   **Bash**: 동일한 수정을 수행하는 셸 스크립트를 생성합니다.
*   **SCAP**: CCE ID(`80551-5`)를 메타데이터에 포함하여 표준 준수성을 식별합니다.

이러한 구조는 `utils/generate_profile.py`에서 볼 수 있듯이, 외부 표준(NIST, PCI-DSS 등)의 컨트롤을 YAML 규칙과 매핑하는 과정에서도 일관된 데이터 구조를 유지하는 데 기여합니다.

## 대안과 비교했을 때의 장단점

### ComplianceAsCode vs. 수동 관리 또는 단일 포맷 도구

*   **장점**:
    *   **다양한 포맷 지원**: 하나의 규칙으로 Ansible, Bash, SCAP 등을 동시에 생성하므로, 조직의 다양한 도구(스캐너, 구성 관리 도구)에 유연하게 대응할 수 있습니다.
    *   **표준 준수성**: NIST, STIG, CIS, OSPP 등 주요 보안 표준을 공식적으로 지원하며, CCE, CPE 등 표준 식별자를 통합 관리합니다.
    *   **자동화된 테스트**: GitHub Actions를 통해 다수의 리눅스 배포판에서 규칙의 유효성을 자동으로 검증합니다.
*   **단점**:
    *   **복잡성**: 빌드 시스템이 복잡하여, 새로운 규칙을 추가하거나 기존 규칙을 수정하는 데 있어 프로젝트의 구조와 빌드 프로세스에 대한 이해가 필요합니다.
    *   **학습 곡선**: YAML 규칙의 템플릿 구문과 빌드 시스템을 익히는 데 시간이 소요됩니다.

### ComplianceAsCode vs. 다른 오픈소스 보안 도구 (예: OpenSCAP 자체)

*   **OpenSCAP**는 주로 SCAP 콘텐츠를 *평가(Scan)*하는 도구인 반면, ComplianceAsCode는 콘텐츠를 *생성(Create)*하는 프로젝트입니다. 두 프로젝트는 상호 보완적입니다. ComplianceAsCode가 생성한 콘텐츠를 OpenSCAP로 스캔하는 것이 일반적인 사용 패턴입니다.

## 보안·라이선스·도입 시 확인할 점

*   **라이선스**: 프로젝트는 **BSD-3-Clause** 라이선스를 따릅니다 ([LICENSE](https://github.com/ComplianceAsCode/content/blob/master/LICENSE)). 이는 상업적 사용, 수정, 재배포를 허용하는 관대한 라이선스로, 기업 환경에서의 도입에 유리합니다.
*   **보안**:
    *   **공급망 보안**: `pyproject.toml`에서 `setuptools`, `pyyaml`, `Jinja2` 등 주요 의존성을 명시하고 있습니다. 빌드 시 이러한 의존성의 버전을 주시해야 합니다.
    *   **콘텐츠의 정확성**: 생성된 보안 규칙의 정확성은 프로젝트 커뮤니티와 표준 기관(DISA, NIST 등)의 검토에 의존합니다. 도입 전에는 조직의 요구사항에 맞게 규칙을 커스터마이징하고 테스트해야 합니다.
    *   **CPE 데이터**: `build-scripts/cpe_generate.py`는 CPE 데이터를 처리하는 데 사용되며, 이는 시스템 식별의 정확성에 직결되므로 주의가 필요합니다.
*   **도입 시 확인점**:
    *   **플랫폼 지원**: 지원하는 OS 버전(RHEL 8/9, Ubuntu 22.04/24.04 등)이 조직의 환경과 일치하는지 확인해야 합니다.
    *   **빌드 환경**: 소스에서 빌드하려면 `CMake`, `Python 3.6+`, `Jinja2`, `PyYAML` 등이 필요합니다.

## 한계와 추천 대상

*   **한계**:
    *   **커뮤니티 의존성**: 표준 업데이트(STIG, NIST 등)에 대한 콘텐츠 업데이트는 커뮤니티의 기여에 크게 의존합니다. 최신 표준을 빠르게 반영하기 위해서는 프로젝트의 업데이트 주기를 모니터링해야 합니다.
    *   **커스터마이징의 어려움**: 대규모 조직에서 자체적인 보안 정책을 추가하려면 YAML 규칙을 새로 작성하거나 기존 규칙을 수정해야 하며, 이는 프로젝트의 빌드 시스템을 이해해야 가능합니다.
    *   **Windows 지원 부재**: 현재는 리눅스 배포판과 Firefox 등 일부 애플리케이션에 집중되어 있으며, Windows 운영체제는 공식적으로 지원되지 않습니다.

*   **추천 대상**:
    *   **리눅스 기반 보안 준수 조직**: NIST, STIG, CIS 등 표준 준수가 필요한 기업이나 기관.
    *   **자동화된 보안 관리 추구 조직**: Ansible, Bash 등을 통해 시스템의 보안 상태를 자동으로 수정하고 평가하려는 DevSecOps 팀.
    *   **보안 콘텐츠 개발자**: SCAP, OVAL, XCCDF 표준에 대한 이해가 있고, 보안 규칙을 프로그래밍적으로 관리하고 싶은 개발자.

이 프로젝트는 보안 자동화의 표준을 제시하며, 특히 리눅스 환경에서 다각도의 보안 준수와 자동화를 원하는 조직에게 강력한 솔루션을 제공합니다.
